# Gateway P0 implementation plan

**Goal:** Deliver the approved gateway P0: immediate chat stop/status and project-scoped task list/status/result/stop across Feishu, WeCom and WeChat.

## Design decisions

- Owner: a shared gateway message-queue class owns per-chat pending/active execution state; each transport owns one instance. GatewayTaskCommands remains the owner of gateway-launched task execution. ProjectTaskStore remains the owner of durable task state.
- Command path: authenticated/deduplicated ingress -> immediate control commands or serial message queue -> existing handler. No new routes or dependencies outside server-services.
- Ordering: slash `/stop`, `/abort`, `/status`, and `/task list|status|result|stop` bypass ordinary messages. Stop cancels the current chat's queued messages and signals active preparation as well as aborting its session; it never resets history or stops independent tasks. Abort waits are bounded. New messages after stop remain queued behind actual execution settlement so two prompts never overlap.
- Task scope: commands resolve titles or last-list numbers within the currently allowed project. Existing natural-language waiting-list/start behavior stays compatible. Slash `/task list` includes all task states. Result reads existing live/persisted session messages, never resumes execution. Stop only controls executions owned by GatewayTaskCommands and does not claim to cancel unrelated WebUI/queue work.
- Derived views: chat status shows execution state, elapsed seconds, pending count. Task status distinguishes persisted inbox state from current running state; completed prompt execution is not automatically marked completed in the inbox.
- Recovery: chat queue state is ephemeral. Task records/transcripts remain durable; after restart report execution not active rather than infer success from `started`. Number snapshots require re-listing after restart.

## Implementation and validation

1. Add failing shared queue tests: immediate status projection, pending cancellation, stop during preparation, subsequent-message serialization, per-chat isolation; implement minimal queue owner.
2. Add failing three-transport integration tests proving `/stop` and `/status` bypass a blocked prompt and preserve sessions; integrate queue and controls, plus all help text.
3. Add failing GatewayTaskCommands tests for all-state list, title/number targeting, result extraction (live and persisted), safe stop/repeat, project boundaries and ambiguous/stale targets. Extend existing command intent parser with deterministic task slash dispatch and natural-language task status/result/stop.
4. Update both language versions of all three gateway manuals, including exact stop semantics and task status limitations.
5. Run focused gateway tests, server build, architecture check/tests, then workspace build/test. Review diff for security, cancellation and stale-result races. No automatic commit or deployment.
